## 1. Purpose & scope

A single-user webapp that helps the human write blogs/articles, letters, reports and docs (INT-001). Writing work is organized as **projects** containing read-only Markdown resource trees the human reads and annotates (INT-002). A joint human–AI **reading round** over a chosen set of docs runs AI **expert lenses** whose notes the human reviews, discards, or adopts (possibly modified) into their own notes, and ends in a human-curated **notes dump** (snippets, highlights, human thoughts, AI thoughts) (INT-003). A **button** generates a report from the dump, then the app **shifts to an editor mode** where the report is edited manually paragraph-by-paragraph, with per-block AI options: a tone change producing **5 samples** and an argument **critique/challenge** (INT-004). The generated report is also readable in a **view mode** — a rendered, non-editing reading surface available alongside the block editor, which stays the typing surface (INT-005). The app's AI calls can be served by **two live providers** behind one boundary — the AnthropicVertex path and **DeepSeek** (OpenAI-compatible, model deepseek-v4-flash, selectable instead of claude-sonnet-5) — with the choice made **per project through an in-app selector**, not an environment variable (INT-007). The whole app finally runs as a **single containerized webapp** on the human's machine — one container serving the built frontend and the FastAPI backend together, **no docker compose** (DEC-019) — **exposed publicly through a Cloudflare tunnel** at `writer-assistance.rohanawhad.com` (DEC-020, H34, H36), protected by a **minimal in-app API-key login**: a custom login screen served by the app with a session cookie (DEC-021, DEC-022), booting with a **fresh database on a named Docker volume**, never the existing local data (DEC-023) (INT-006). Resources enter a project by **uploading Markdown files from the browser** — a client-side file picker used at project setup; the import never reads or addresses the server's filesystem (INT-008, DEC-028) — and DEC-016's immutable-snapshot storage is unchanged. The app's **web view is mobile-friendly**: the same single-user surface — projects, resources, rounds, curation, report editing and viewing, provider selection, and the INT-006 gate — is **usable on phones and on an iPad** (INT-009, H37: today the view is unusable on a mobile, and it must work on an iPad as well).

**Non-goals** (deliberate exclusions — no human evidence mandates them): authentication **beyond INT-006's single-user API-key gate** (no multi-user, accounts, roles, signup, or password management — DEC-021/022 add a single-user login and nothing more); multi-user, teams, sharing, roles; billing/plugins/marketplaces; mobile apps; any editing/deleting/renaming/write-back of resource files; non-Markdown resource types; import from a **server-filesystem path** (the pre-INT-008 JSON `{"path": …}` import is **removed** by DEC-028 and must not resurface — import is browser upload only, R-079); real-time collaboration; document export beyond minimal Markdown download (see §9 OQ-04). The app is **local single-user** (human-resolved 2026-09-03) — DEC-014's "no authentication, no hosting" is **amended by INT-006**: the app gains a single-user auth gate (DEC-021/022) and public exposure through a Cloudflare tunnel (DEC-020), served by one container (DEC-019) with a fresh volume DB (DEC-023); it stays single-user and self-hosted — no multi-user anything, no Cloudflare Access layer (the app's own login screen is the gate). View mode (INT-005) is a **reading surface, not a review/comment mode**: no annotations/comments/markup on the report and no per-block AI actions inside view mode (design note — SD-19; DEC-018 mandates a non-editing rendered reading surface, it does not mandate review features). Mobile responsiveness (INT-009) adds **no new product features and no new desktop functionality**: it makes the existing surface (R-001..R-081 behaviors) usable on phone and tablet viewports — no new backend endpoints, no new data entities, no offline mode, no PWA, no native/mobile apps; the shipped artifact is unchanged (the same built SPA of R-076, served the same way), and desktop (≥ 1024 CSS px) behavior is untouched.

### 2.2 Projects and resources — INT-002

- R-010: A **project** contains a tree of directories/files/sub-directories of **Markdown files**, which act as that project's **resources**. `Trace: DEC-005` (Scope note — since v1.9 the only import path is the browser upload, whose accepted files land **flat** at the project root; import creates no directory nodes (SD-28). - R-011: Resources are **read-only for the human**: the human reads them and makes notes/highlights; resources themselves are **never edited** by the app or the human through the app. The UI must expose no edit affordance for resource content. `Trace: DEC-005, DEC-006`

How Markdown files enter a project is INT-008's mechanism: **import = browser upload at project setup** (R-079..R-081, §2.10); DEC-016's immutable-snapshot semantics are unchanged.

### 2.3 AI expert lenses and their notes — INT-003

- R-020: The AI **reads the resources** and, per doc, **proposes relevant expert lenses** for that doc — e.g. financial, real-estate, political, software-engineering — as appropriate to content. `Trace: DEC-007`
- R-021: Each chosen lens runs as an **AI expert that keeps its own notes** about the doc(s) it read. Expert notes are stored distinctly from human notes, attributable to (project, reading round, doc, expert). `Trace: DEC-007, DEC-008` (Storage shape: `Depends on soft ASM-002`.)
- R-022: The human can **review expert notes**, **discard them**, or **add them (possibly modified) to the human notes**. Merged items keep provenance of their origin so the dump can still show AI-vs-human authorship where relevant. `Trace: DEC-008` (Review mechanics: `Depends on soft ASM-003`.)

### 2.4 Reading round and curated notes dump — INT-003

- R-030: A **reading round** operates on a **set of docs** the human chooses from the project resources; the human and the AI read that set together (AI's contribution enters via expert notes and AI thoughts). `Trace: DEC-009`
- R-031: The **human curates** the round's output as a **notes dump** that may contain: snippets, highlights, human thoughts, and AI thoughts. Curation means the human selects/orders/composes these items; the dump is persisted per round. `Trace: DEC-009` (Curation UX — ordered typed entries from per-doc pools + free typing: `Depends on soft ASM-008`.)

### 2.5 Report generation and mode shift — INT-004

- R-040: A **button** ("Generate report") creates the report **from the curated notes dump** of the round (a single AI call whose input is the dump content). `Trace: DEC-010`
- R-041: The generated report is stored at **paragraph granularity**: the paragraph is the unit **block**. `Trace: DEC-011` (Block storage: `Depends on soft ASM-004`.)
- R-042: **After report creation the round shifts to editor mode**: that round's **round-bound** reading operations — running its experts, curating its dump — are closed/disabled, and the report becomes the editing surface. Annotating is **not round-bound**: annotations are resource-scoped (DEC-006; §4 `Annotation`), so the shift closes no annotation capability and docs stay annotatable wherever they are read, including from new rounds over the same resources. `Trace: DEC-010, DEC-011`
- R-043: In editor mode the human edits the report **manually, paragraph by paragraph** (block by block); typing is the primary edit path. `Trace: DEC-011`

### 2.6 Per-block AI assistance in editor mode — INT-004

- R-050: Per block, option (a) **change of tone**: the AI generates **5 samples in different tones** for that block, **based on the context of the report** (not the block alone). `Trace: DEC-012`
- R-051: Tone samples only change block content by explicit human action (e.g. preview → apply one sample); the samples themselves never auto-replace text. `Trace: DEC-012, DEC-011`
- R-052: Per block, option (b): the AI **critiques and challenges the argument** of that block so the human can formulate it better. Critique output does not auto-edit the block; the human rewrites manually. `Trace: DEC-013, DEC-011`
- R-053: Both per-block assists use the report context as AI input (target block text plus report context). `Trace: DEC-012, DEC-013`

### 2.7 View mode — INT-005

- R-060: The generated report is readable in a **non-editing view mode** — a **rendered reading surface**, in the style of the resource reading view (SD-2) — as an **alternative** to the block editor, alongside the existing editing mode. `Trace: DEC-018`
- R-061: View mode is **non-editing**: it exposes **no typing surface and no edit affordances** for report content; the block editor remains the typing surface of the report. `Trace: DEC-018`

Surface mechanics DEC-018 does not settle are agent-owned (SD-18, SD-19 below); none of them adds a stage or changes the round's stage model (SD-9) or the DEC-011 mode shift.

- **SD-18 (agent-owned — how the modes coexist and switch)**: view mode is a UI sub-mode of the report surface, available whenever the round's report exists (i.e. in the `editing` stage, SD-9). The report header offers a View/Edit switch; entering the report surface still lands on the **editor**, preserving DEC-011's shift-to-editor (DEC-018 positions view as an alternative, not a default). The chosen sub-mode is **ephemeral client state — not persisted** (no per-round/per-report mode column), and switching surfaces never writes data and never changes the round's stage. Rationale: DEC-018 settles neither the switch affordance, the default mode, nor toggle persistence; landing on the editor honors DEC-011's shift semantics while view stays one click away.
- **SD-19 (agent-owned — what view mode renders and offers)**: view mode renders each `ReportBlock`'s saved content read-only as a rendered surface (same rendering approach as the resource reading surface, SD-2). It shows no textareas, no per-block save state, and no per-block AI assist controls (tone change, critique — those stay in the editor); the report header keeps the export/download action (a read-only operation) while delete stays on the editor surface (it mutates state). When the human switches from editor to view, a dirty block is flushed first (existing save-on-blur semantics, R-043) so view mode never renders stale text for a block just edited. Rationale: DEC-018 mandates readability without an editing surface; the exact chrome and the flush behavior are agent-shaped.

### 2.8 Dual live AI providers — INT-007

- R-070: The app runs **two live AI providers** behind the R-004 boundary: (a) the **AnthropicVertex provider** (kept; DEC-004/DEC-017) and (b) **DeepSeek** — an **OpenAI-compatible** provider with model **deepseek-v4-flash**, **selectable instead of claude-sonnet-5** — reached at the **api.deepseek.com** endpoint. Both providers implement the same AIClient contract, so lens proposals, expert reads, report generation, tone samples and critiques work identically over either; which provider serves a call is the provider selected for the call's project (R-071). `Trace: DEC-024, DEC-025`
- R-071: Provider choice is made **in-app via a selector, not an environment variable**, and is persisted **per project**: the project row carries the selected provider, used for **every AI call made for that project's resources and rounds**. A **fresh project defaults to `deepseek`**, and the human can change the selection at any time. `Trace: DEC-027, DEC-024` (Selection unit — per project vs per round — is the agent-resolved door OQ-08; SD-20. Fresh-project default rationale: DEC-024 has deepseek-v4-flash replace claude-sonnet-5 in role and the human wants the move (H26), so new projects start on DeepSeek; vertex stays one click away — SD-20.)
- R-072: Provider configuration comes from environment variables loaded via `backend/.env` (DEC-015 precedence), with **both providers' names documented in `backend/.env.example`**: the existing vertex names (RES-001) plus, for DeepSeek, `DEEPSEEK_API_KEY` (the DeepSeek API key — DEC-026) and `DEEPSEEK_MODEL` (R-073). `Trace: DEC-026, DEC-015`
- R-073: The DeepSeek **model id is read from the `DEEPSEEK_MODEL` env var and defaults to `deepseek-v4-flash` when unset**; it is never hardcoded as a non-configurable constant. `Trace: DEC-024` (`Depends on soft ASM-012` — whether api.deepseek.com accepts the literal id `deepseek-v4-flash` is unverified (alias-form risk, cf. `claude-opus-4-8[1m]` on Vertex); the env override lets a live probe fix the id without code change.)
- R-074: When an AI call is made for a project whose **selected provider is not configured at call time** (its required env names are missing), the call **fails fast with a clear config error** — the existing `ConfigError` semantics (HTTP 503, `{"detail": ...}` naming the missing names). The app **never falls back to the other provider, never retries against it, and never ignores the failure**; projects whose selected provider is configured are unaffected. `Trace: DEC-024, DEC-026` (Mirrors today's vertex behavior: `read_vertex_settings` → `ConfigError` → 503 through the app's ApiError handler (app/errors.py); provider runtime/transport failures stay `AIError` → 502. The R-004 boundary and its failure semantics are unchanged.)

Provider mechanics DEC-024..DEC-027 do not settle are agent-owned (SD-20, SD-21 below); none of them changes the offline test story (fakes implement `AIClient`; SD-16) or adds a persisted entity beyond one project column (§4).

- **SD-20 (agent-owned — resolved door OQ-08: selector granularity, defaults, existing projects)**: the selector is **per project** — a `deepseek`/`vertex` value persisted on the project row and used for all AI calls in that project's resources and rounds. Rationale: the project is the smallest coherent unit whose AI behavior should be uniform (a call never straddles two providers), and a project-level default avoids mid-round surprises; a per-round override can be added later without storage loss (two-way door). Fresh projects default to **`deepseek`**: DEC-024 has deepseek-v4-flash replace claude-sonnet-5 in role and the human wants the move (H26); vertex stays selectable (DEC-024 keeps it live). **Existing projects** adopt the column default (`deepseek`) when the schema is next initialized; only their subsequent AI calls are affected — no artifact is rewritten — and each project can be switched back in-app at any time.
- **SD-21 (agent-owned — provider-resolution mechanics at the R-004 boundary)**: the AIClient protocol (app/ai/client.py), the five call kinds, and the prompts/parsers are provider-agnostic and unchanged; each provider is a thin AIClient implementation over its own transport (vertex: the existing `AnthropicVertex` SDK client with the model/small-model split per RES-002; deepseek: an OpenAI-compatible transport at `api.deepseek.com` (DEC-025), with both the large and the small-fast call classes routed to the single `DEEPSEEK_MODEL` id until a second DeepSeek model exists). Resolution happens at call time: the caller already holds project context (a resource, round, or report resolves to its project), reads `projects.ai_provider`, and uses the matching implementation; implementations are built lazily and cached per provider (today's `get_ai_client` singleton pattern generalizes to one cache per provider). A provider is only built when a project selects it, so an unconfigured provider can never break calls for projects on the other one (R-074); the choice is read from the DB per request — switching takes effect on the next AI call with no restart and no env var (DEC-027). A selected provider whose env is incomplete raises `ConfigError` (503) at build time, surfacing unchanged through the app's ApiError handler.

### 2.9 Auth gate, static serving, and container deployment — INT-006

- R-075: The app enforces a **single-user auth gate** whenever it is created with an **`AUTH_API_KEY`** (read once at app creation; DEC-021). With the gate active, every request except the **login surface** requires a valid session: `/api/v1/*` requests without one return **401 `{"detail": "authentication required"}`** (the app's existing `{detail}` error shape — the SPA api client surfaces it as `ApiError(401, …)`, which is all `frontend/src/api/client.ts` does today), and every other protected path (page and asset navigations) returns **302 → `/login`**. Normative target (part of the auth-gate milestone's frontend work; it does not exist at v1.8): the SPA must treat any 401 on a data call as logged-out and navigate to the login page. The login surface is served **by the app itself** (DEC-022 — a custom login screen, not browser Basic Auth): `GET /login` returns a minimal **server-rendered HTML login page**; `POST /login` validates the submitted `key` against `AUTH_API_KEY` with a constant-time comparison and, on success, sets an **HttpOnly session cookie** (`wa_session`) and redirects to `/`; a wrong key returns 401 with the login page re-rendered with an inline error and **no cookie set**. `POST /logout` clears the session cookie. Sessions are verified **per request** and survive page reload. When the app is created **without** `AUTH_API_KEY` the gate is **inactive**: no login endpoints, no session checks, no gate 401/302 behavior — the app behaves exactly as before INT-006 (the offline test story and key-less local dev flow are untouched; SD-24). `AUTH_API_KEY` is documented in `backend/.env.example`. `Trace: DEC-021, DEC-022` (login surface and response-split details: SD-22; session mechanism: SD-23; gate-active rule: SD-24.)
- R-076: **Static serving of the built SPA** (DEC-019: one container serves frontend + backend together): when `frontend/dist` exists at app creation the FastAPI app serves it — `/` → `index.html`, `/assets/*` → the built hashed files, and any other GET path that is neither an API route nor an existing file → `index.html` (SPA fallback). The API keeps its **`/api/v1` prefix unchanged**; **unknown API routes keep today's 404 behavior** for requests that pass the gate (the gate runs first — R-075 — and the SPA fallback must never swallow `/api/*` paths). No dist directory → no static mount (test factories and build-less dev runs are unaffected). The **local dev flow is unchanged** — the two run modes are (a) dev servers: vite on :5173 (its proxy forwards `/api` plus `/login` and `/logout` to uvicorn on :8000, so the login surface is reachable in dev; SD-22) + uvicorn on :8000, and (b) the single container (R-077), the only mode where FastAPI serves the built SPA. `Trace: DEC-019` (mount shape: SD-22; directory resolution: SD-25.)
- R-077: **Container packaging**: one **multi-stage Dockerfile at the repo root** — stage 1 (node): `npm ci` + `npm run build` in `frontend/` (build → `frontend/dist`); stage 2 (python `3.13`-slim, matching `backend/.python-version`): backend dependencies from the lockfile **without the dev group** (`uv sync --frozen --no-dev`; SD-25), the backend app code, and the built `frontend/dist`; the app runs as a **non-root user**. The image **bakes in no secrets** (ASM-014): no `.env`, no key material — every runtime value arrives via `docker run -e`/`--env-file` (`AUTH_API_KEY`, the vertex env names per RES-001, and `DEEPSEEK_API_KEY`/`DEEPSEEK_MODEL` per R-072; all documented in `backend/.env.example`). CMD serves the app with **uvicorn on `127.0.0.1:8000`** from the `backend/` workdir; `EXPOSE 8000` documents the port (SD-26). A repo-root **`.dockerignore`** excludes `.env`, `data/`, `node_modules`, `dist`, `logs/`, `.hai/`, `.git`. **No docker compose anywhere** (DEC-019). The SQLite DB lives on a **named Docker volume** (DEC-023): the runbook mounts the volume at `/data` and sets **`WRITER_ASSISTANCE_DB=/data/writer-assistance.db`** (the app's existing `ENV_DB_PATH`, `app/main.py`); first boot on an empty volume gets a **fresh database** — the existing lifespan schema init (`create_app` lifespan → `db.init_schema`, app/main.py) creates the tables on every start, so no seed step exists; the pre-existing local `backend/data/` DB is never mounted in. `Trace: DEC-019, DEC-023` (image details: SD-25; network shape: SD-26.)
- R-078: The container **fails closed**: the image's entrypoint requires `AUTH_API_KEY` — when it is unset or empty at boot the process **exits immediately with a clear error and serves nothing**. A container exposed on a public hostname can therefore never run gate-open; the gate-inactive mode (R-075) stays a dev/offline affordance that the image never exercises. The containerized run requires `AUTH_API_KEY`, and the public-exposure done-gate (§11.3) verifies the public hostname 401s without login. `Trace: DEC-021` (exact rule: SD-24.)

Deployment mechanics DEC-019..DEC-023 do not settle are agent-owned (SD-22..SD-27 below). None of them changes an R-001..R-074 behavior, adds a persisted entity (§4), or disturbs the offline test story: gate-off instances are the default everywhere except the production entry point (SD-24), and the gate tests construct instances with an explicit key.

- **SD-22 (agent-owned — login surface and 401-vs-302 split)**: the login surface is a **server-rendered minimal HTML page** at `GET /login` (self-contained markup; no SPA assets) with a plain form posting to `POST /login` (`application/x-www-form-urlencoded`, field `key`) — chosen over an SPA login route because everything, SPA assets included, sits behind the gate (R-075): a logged-out visitor must never receive `index.html`, so an SPA-delivered login screen would be unreachable without serving the app open; server-rendered keeps the entire auth surface inside FastAPI. Response split: `/api/v1/*` → 401 JSON (API callers; the SPA already models non-2xx as `ApiError` with `status`), everything else → 302 `/login` (human navigations); `GET /login` with a valid session → 302 `/`. The login/logout routes are registered **only when the gate is active**, so a gate-off instance exposes nothing new (`/login` → 404). Dev mode: the vite proxy forwards `/login` and `/logout` alongside `/api` (R-076), so the same flows work at :5173 — the session cookie lands on the dev origin and the proxied requests carry it.
- **SD-23 (agent-owned — session mechanism)**: a **stateless HMAC-signed session cookie** — no sessions table, no server-side state, nothing persisted (§4 unchanged), and **no new secret**: the signing key derives deterministically from `AUTH_API_KEY` as `HMAC-SHA256(AUTH_API_KEY, b"writer-assistance-session-v1")`. Cookie `wa_session` value is `<base64url(json {"exp": <unix seconds>})>.<hex hmac>`; verification runs per request — the signature is recomputed and compared with `hmac.compare_digest`, then `exp` is checked to be in the future. Validity: **30 days from login** (fixed; single-user browser save per DEC-021/H27). Attributes: `HttpOnly`, `SameSite=Lax`, `Path=/`; **`Secure` is set only when the request arrived over https** (scheme `https`, or `X-Forwarded-Proto: https` — trusted only because the listener is loopback-bound, SD-26/SD-27): local http smoke runs and dev keep a usable cookie, while the public tunnel gets a Secure one. Stated consequences: container **restart does not log the browser out** (the stateless cookie re-verifies; in-memory or DB-backed sessions would reset on restart and need a table — the signed cookie is the smallest consistent option); **rotating `AUTH_API_KEY` invalidates all sessions** (the key rotates the signing key), so the runbook keeps `AUTH_API_KEY` fixed (it is fixed in `backend/.env`, DEC-021/OBS-005).
- **SD-24 (agent-owned — gate-active rule, fail-closed)**: the gate is decided **once per app instance at creation**: `create_app()` is gate-off by default; the module-level production app (`app.main`) resolves `AUTH_API_KEY` from the environment **after** `load_dotenv(override=True)` (DEC-015) and passes it in — uvicorn runs are gated exactly when the key is present, and tests choose per instance (`create_app(auth_key=...)` for gate-on suites, plain `create_app()` for everything else). CI stays key-less and offline (SD-16). `backend/.env` on the human's machine already holds `AUTH_API_KEY` (OBS-005), so **local dev runs are gated too** — the §11.2 precondition covers the one-time browser login, and removing the key from `.env` restores the open local flow (two-way door). The **container entrypoint adds the fail-closed rule**: a two-line shell check in the Dockerfile CMD exits 1 with a clear "AUTH_API_KEY is required" message when the var is empty, before uvicorn starts (R-078). Rationale: cheap and testable (`docker run` without the key → non-zero exit, nothing listening on 8000), and it converts the dangerous misconfiguration — an open app on a public hostname — into a loud boot failure.
- **SD-25 (agent-owned — image runtime details)**: runtime stage `python:3.13-slim` (matches `backend/.python-version`); uv is installed in the image; dependencies are installed with `uv sync --frozen --no-dev` from `backend/` (copy `pyproject.toml` + `uv.lock` first for layer caching, `app/` after) — the dev group (pytest/mypy/ruff) is excluded from the image. The app runs as a **non-root `writer` user (uid 1000)** that owns `/app`; the `/data` mountpoint is created and chowned to it in the image so a fresh named volume inherits writable ownership. Static directory: the app factory's static mount defaults to `../frontend/dist` relative to the backend working directory — the image layout (`/app/backend` + `/app/frontend/dist`) makes the default correct with no extra env; no env override in v1 (two-way hook if the layout ever changes). DB directory: `WRITER_ASSISTANCE_DB` points at `/data/writer-assistance.db`; the lifespan's `mkdir(parents=True)` (app/main.py) already creates the parent inside the volume.
- **SD-26 (agent-owned — network shape)**: the container runs with **`--network host`** and uvicorn binds **`127.0.0.1:8000`** — the container listens exactly on the host loopback (ASM-015's shape: LAN-invisible, no `-p` mapping, no docker NAT). This is the only shape in which host cloudflared's `http://localhost:8000` service URL reaches a loopback-bound uvicorn: with the default bridge network and `-p 127.0.0.1:8000:8000`, docker-proxy connects to the container's eth0 IP and a 127.0.0.1-bound listener refuses the connection. Tradeoff stated: host network namespace sharing is acceptable for one container on a single-user host whose only external path is the tunnel; `EXPOSE 8000` is documentation (no published port). Fallback if the host cannot use `--network host`: bridge network + uvicorn `--host 0.0.0.0` inside + `-p 127.0.0.1:8000:8000` (identical external posture; ASM-015's literal "binds only 127.0.0.1" then does not hold — reviewer note).
- **SD-27 (agent-owned — threat model, CSRF, proxy trust)**: the gate is a **single-user convenience gate over a 256-bit random key** (`secrets.token_urlsafe(32)`, OBS-005), not a defense against determined attackers: no rate limiting, no lockout, no CSRF token. CSRF posture: `SameSite=Lax` + HttpOnly cookie + a JSON-only API covers the state-changing surface; the two form-posting endpoints (login, logout) are the only cross-site-reachable ones, and login grants no more than knowledge of the key already does. `X-Forwarded-Proto` is trusted for the Secure-flag decision only because the listener is loopback-bound (SD-26), so the only possible proxier is cloudflared. Reviewer note: if cloudflared does not forward `X-Forwarded-Proto` for the tunnel's localhost service URL, the cookie simply stays non-Secure on the public origin — functionally correct (the public path is https-only; Secure is belt-and-braces) — verify during §11.2 step 23. The R-079 multipart import endpoint adds no third form-posting surface: a cross-site form submission carries no `wa_session` (SameSite=Lax → 401) and a file-less part cannot satisfy the multipart contract (422), so the CSRF posture is unchanged.

### 2.10 Resource import by browser upload — INT-008

- R-079: The project-import endpoint is a **browser upload**: `POST /api/v1/projects/{project_id}/import` accepts **`multipart/form-data`** with one or more file parts (field name `files`), each carrying a Markdown file the human picked in a **client-side file picker** in the workspace. The request never contains a server-filesystem path, and the backend never reads the server filesystem to import resources; the pre-INT-008 JSON body `{"path": "<server-side absolute path>"}` is **removed** — the route no longer parses it, and no UI, test, or fixture may pass one. Import stays a project-setup action over DEC-016's snapshot semantics (R-081). Uploads are ordinary `/api/v1` calls behind the INT-006 gate: when the gate is active they require the session cookie exactly like every other endpoint (R-075), carried same-origin through the vite dev proxy or the container/tunnel (R-076); no new auth surface is added, and gate-off instances behave as before. `Trace: INT-008, DEC-028`
- R-080: The upload imports **Markdown files only** — the per-part acceptance rules (extension set, name shape, encoding, empty files) and their rejection shapes are the agent-owned grammar of SD-30. Every accepted file is **snapshotted byte-for-byte into the immutable snapshot** (DEC-016): one file node at the project root with `path == filename` (SD-28) and its content stored in `resource_docs` — the same storage as before, with unchanged read-only guarantees (R-011); a rejected request persists nothing (all-or-nothing). `Trace: INT-008, DEC-028, DEC-016`
- R-081: Import remains a **one-shot setup action** (DEC-016's at-project-setup semantics): a project that already has file resources rejects any further import with **409** `{"detail": …}`, unchanged from the pre-INT-008 conflict behavior. An unknown project is a **404**. Success returns **201** with the unchanged `ImportResult` shape `{"project_id": …, "imported_files": …}` (files imported by this request). Intra-request duplicate names are handled per SD-30. `Trace: INT-008, DEC-028, DEC-016`

Import mechanics DEC-028 does not settle are agent-owned (SD-28..SD-30 below). None of them adds a persisted entity (§4) or disturbs the offline test story: uploads are exercised through the TestClient's multipart API, gate-off by default (SD-24), with one gate-on 401 test.

- **SD-28 (agent-owned — flat placement; no folders in v1)**: uploaded files land **flat at the project root**: each file node gets `path == filename` and `parent_id` NULL, because a plain browser file picker (`<input type="file" multiple>`) delivers file names, not relative paths — there is nothing to derive directories from. The tree data model (DEC-005/R-010, §4 `resource_nodes`) is untouched: dir nodes stay representable, snapshots imported before INT-008 keep rendering their folders, and the left-panel tree UI needs no change. If the human later wants folders from uploads, an "upload folder" mode could read `webkitRelativePath`/directory-picker entries and create dir nodes — a two-way door with no storage change.
- **SD-29 (agent-owned — size cap and its error)**: a per-import **total size cap of 10 MiB** guards the snapshot DB and the publicly exposed surface (INT-006): a request whose multipart body exceeds the cap is rejected with **413 `{"detail": "import upload exceeds the 10 MiB cap"}`** (a `413` subclass of the app's `ApiError` family, so the uniform `{detail}` shape and app/errors.py handling are kept) and nothing persists. The cap is settable at app creation for hermetic tests (alongside `db_path`/`auth_key` in `create_app`), defaulting to 10 MiB in production; a single file over the cap is rejected by the same rule.
- **SD-30 (agent-owned — acceptance grammar; two-way, reversible)**: a file part is accepted when its name ends in `.md` or `.markdown` (case-insensitive), is otherwise plain (no path separator, not dot-leading), and its bytes decode as UTF-8; an empty (zero-byte) `.md` file is accepted and snapshotted with empty content (as the pre-INT-008 tree scan handled empty files). A part failing any check rejects the **entire** request with **400 `{"detail": …}`** naming the offending file; a request yielding no accepted file at all is rejected — the framework's standard 422 when the multipart body has no usable part, or 400 when parts exist but none passes (mirroring the pre-INT-008 "no Markdown files" failure); duplicate file names within one request reject the whole request with **409** (the snapshot's `UNIQUE (project_id, path)`). Every rejection persists nothing. Rationale: reviewer round (S8-1) moved this grammar out of R-080/R-081, which keep only the record-backed core; the grammar is reversible without touching DEC-016 storage or the INT-008/DEC-028 contract (e.g. dropping `.markdown` or the dot-leading rule later is a one-line change).

### 2.11 Mobile-friendly web view — INT-009

- R-082: The app's web view is **usable on a phone** — at a **phone-width viewport** (SD-31: 320–767 CSS px) the human can (a) read any resource or report content in full, (b) reach every surface — the projects list, the workspace, the round modes (read & annotate, curate dump, report), the report's view/editor sub-modes, and every dialog (new project, delete project, import, new round, delete report) plus the login screen when the gate is active — and (c) trigger every core action: open/create projects, browse resources and rounds, highlight and note, propose/select lenses and run experts, review expert notes, save a dump, generate a report, edit blocks, tone change, critique, view-mode switch, export, provider select, import upload, login/logout — **without horizontal page scrolling and without clipped or unreachable controls**. No interaction requires a desktop-width layout. `Trace: INT-009` (width classes: SD-31; per-class surfaces: SD-32; touch legs: SD-33.)
- R-083: The app's web view is **usable on an iPad**: at a **tablet-width viewport** (SD-31: 768–1023 CSS px, covering iPad portrait at 768) and at **iPad landscape** (1024+ CSS px, the desktop tier), the R-082 core actions and dialogs work through the same touch interactions, and resource/report text remains readable at a comfortable measure without horizontal scrolling on any surface. `Trace: INT-009` (width classes: SD-31; per-class surfaces: SD-32.)
- R-084: The layout **adapts to viewport width changes**: resizing the window or rotating a device between portrait and landscape reflows the active surface to the new width class **without a page reload and without losing what the human is doing** — the open project, active doc, round, and mode survive the change — and no supported width (SD-31) exhibits horizontal page scrolling. `Trace: INT-009` (state preservation is presentation-only; SD-32.)
- R-085: **Touch interactions reach every core action**: on a coarse-pointer (touch) device every control a mouse user has is reachable by tap — no action hides behind hover-only styling (SD-33) — and the touch legs of the reading flow work: long-press text selection on a doc can produce a highlight and an anchored note, and text input (notes, dump entries, block edits, dialog fields) is usable with the on-screen keyboard, with the field being typed into scrolled into view and nothing needed for typing clipped. `Trace: INT-009` (hover policy and selection plumbing: SD-33; automated vs manual coverage: SD-34.)

Adaptation mechanics INT-009 leaves open are agent-owned (SD-31..SD-34 below). None of them changes an R-001..R-081 behavior at desktop widths, adds a backend endpoint (§6 note), or adds a persisted entity or column (§4 note); the blockers they address are concrete fixed-width, fixed-height, hover-only, and mouse-only-event patterns in the current SPA — no media query or responsive utility exists today outside one `sm:` dialog-footer rule (`frontend/src/components/ui/dialog.tsx:55`): the workspace is a fixed three-pane flex (`flex h-screen overflow-hidden`, `WorkspaceScreen.tsx:502`) with a `w-72` sidebar (`LeftSidebar.tsx:177`) and a `w-[360px]` right aside (`WorkspaceScreen.tsx:599`), CurateView lays out as `grid-cols-[1fr_320px]` (`CurateView.tsx:215`), the tone-sample compare is `grid-cols-2` (`ReportEditor.tsx:500`), the annotation delete control is hover-only (`opacity-0 … group-hover:opacity-100`, `AnnotationPanel.tsx:192`), and MarkdownView captures text selection through mouse/key handlers only (`MarkdownView.tsx:285`).

- **SD-31 (agent-owned — device classes and breakpoints)**: three width classes decided by viewport width alone (CSS media queries; no user-agent sniffing), with breakpoints at **768** and **1024 CSS px** (Tailwind `md`/`lg`): phone = 320–767, tablet = 768–1023 (iPad portrait is 768), desktop = ≥ 1024 (iPad landscape is exactly 1024, so it lands in the unchanged desktop tier; iPads in portrait below 1024 — e.g. iPad 9.7–10.9″ at 768 and iPad Pro 11″ at 834 — get the tablet tier, while an iPad Pro 12.9″ portrait at exactly 1024 gets the desktop tier). Rationale: 768 is where today's fixed chrome (sidebar 288 + right pane 360 = 648 px plus padding, `LeftSidebar.tsx:177`/`WorkspaceScreen.tsx:599`) leaves a phone/portrait column unusable, while ≥ 1024 still leaves a usable reading column, so the human-proven desktop layout is preserved rather than re-laid out; 320 is the smallest supported width (no narrower support commitment). Affects R-082..R-084.
- **SD-32 (agent-owned — per-class surfaces and layout adaptation)**: phone: a single-column surface — the workspace chrome that is side-by-side on desktop (resource tree + rounds list; annotation + round panes) moves behind **overlay panels** opened from controls that stay visible on the content surface (e.g. header/back panel toggles), so the reading column keeps the full viewport width; tablet: the content surface keeps full width, with secondary panels available as an overlay or a stacked column at the implementation's choice, provided R-083 holds; desktop ≥ 1024: the existing three-pane arrangement is unchanged. Any fixed side-by-side grid on desktop (CurateView's `[1fr_320px]` pools column, ReportEditor's `grid-cols-2` tone compare) stacks to one column below its class boundary, and `h-screen` chrome (`WorkspaceScreen.tsx:502`) uses dynamic-viewport height handling (with a fallback where unsupported) so bottom-anchored controls are not hidden behind mobile browser chrome. Rationale: the observed blockers are fixed pixel widths/heights and desktop-only grids in four files (list above); overlays keep one full-width reading column instead of squeezing three panes into ≤ 767 px. Affects R-082..R-084.
- **SD-33 (agent-owned — touch parity: hover policy, selection plumbing, tap targets)**: controls styled hover-only for mouse (annotation delete, `AnnotationPanel.tsx:192`) are made visible and operable on coarse-pointer devices (`@media (hover: none)`/Tailwind equivalent); primary row-action tap targets get comfortable sizing (≈ 40–44 CSS px effective; tunable after real-device tryout — two-way). Doc text-selection capture for highlights and anchored notes (MarkdownView listens to `onMouseDown/Up/KeyUp` only, `MarkdownView.tsx:285`) is verified on real touch devices (§11.2 step 26) and extended with pointer/touch or `selectionchange` plumbing **only if** the device leg fails — the exact touch-selection timing differs across iOS/Android browsers, so it is proven by evidence, not assumed. Rationale: hover-hidden affordances and mouse-only event plumbing are the two concrete touch risks found in code; both are reversible implementation doors. Affects R-082, R-083, R-085.
- **SD-34 (agent-owned — verification technique; two-way)**: jsdom (vitest, `css: false` per `vitest.config.ts`) has no layout engine, and no browser e2e harness exists **for the app** (the only Playwright setup in the repo is `.hai/playwright.config.ts`, which covers the hai mission-control viewer — `testDir ./tests`, baseURL `127.0.0.1:4179` — not the SPA), so **layout-level assertions (overflow-free rendering, reflow) are not automatable** in the existing frontend suite; adding an app browser harness is a two-way door not taken in v2.0. Automated coverage therefore proves **JS-observable narrow-mode behavior**: the implementation exposes narrow-mode state through a `useMediaQuery`-style hook over `window.matchMedia`, and the vitest suite mocks `matchMedia` at phone/tablet/desktop widths to assert overlay reachability, control presence, width-change state preservation, and desktop regression. Overflow-freedom and visual reflow are verified manually on emulated viewports and real devices (§11.2 steps 24..26). Affects R-082..R-085 (test map: §11.1).

**Process/lifecycle model** (`SD-9`, agent-derived): the **stage** lives on the round/report, not the project. A round starts in `reading`; when its report is generated, the round shifts to `editing`. Gating is per round: entering `editing` closes that round's round-bound reading operations — running its experts, curating its dump (R-042); annotating is resource-scoped (DEC-006) and stays available project-wide. New rounds in the same project start fresh in `reading`, while an existing report keeps its editor; other rounds are unaffected. No data changes hands between stages except the report itself.

**Concurrency model**: single user, one process; AI calls are HTTP-request-scoped; expert runs within a round may be parallelized (`Depends on soft ASM-002`).

## 5. User flows

- **F1 — Set up project** (R-010, R-011): create project → **import Markdown files by uploading them from the browser** (F15; the upload snapshots them into app storage — human-resolved 2026-09-03/OQ-01, DEC-016 — and import is never a server-filesystem path, R-079) → resources appear read-only. `Trace: DEC-005, DEC-006`
- **F2 — Read & annotate** (R-011, R-012): open a resource in a rendered Markdown view (SD-2); select text to highlight; attach notes; nothing writes back to the file. `Trace: DEC-006`
- **F3 — Lens proposal** (R-020): human asks AI for lenses on a doc; proposals listed per doc; human confirms which to run (SD-3). `Trace: DEC-007`
- **F4 — Expert runs** (R-021): AI experts (one per doc×lens) read the docs and produce their own notes. `Trace: DEC-007, DEC-008`
- **F5 — Expert note review** (R-022): review list per expert with actions: keep / discard / edit-and-add-to-human-notes (provenance preserved) (SD-4). `Trace: DEC-008`
- **F6 — Round curation** (R-030, R-031): human picks the doc set for the round, then curates the notes dump — composing ordered entries of snippets, highlights, own thoughts, and AI thoughts (SD-5). `Trace: DEC-009`
- **F7 — Generate report** (R-040): "Generate report" button → backend calls the AI with the dump → report created as ordered paragraphs. `Trace: DEC-010`
- **F8 — Mode shift** (R-042): the round shifts to editor stage; that round's round-bound reading operations (expert runs, curation) are disabled; annotating docs stays available (resource-scoped, DEC-006); other rounds unaffected. `Trace: DEC-010, DEC-011`

Stack requirements R-001 (FastAPI), R-002 (React + shadcn/ui), R-003 (SQLite), R-005 (no kind-specific logic), and R-072 (both providers' env names documented in `backend/.env.example`) are verified by dependency and static inspection at the §11.3 milestone gates rather than by dedicated automated suites.

**Backend unit tests**:
- AI-client wrapper / provider boundary (R-004, R-070..R-074): with provider transports stubbed or faked, all five call kinds — lens proposal, expert run, report generation, tone samples, critique — route through the provider selected for the caller's project (`vertex` or `deepseek`); assert request payload shape and response parsing are provider-agnostic (shared prompts/parsers). A project selecting `deepseek` without `DEEPSEEK_API_KEY` set fails fast (ConfigError → 503) and never falls back to the vertex client (R-074); the deepseek model id defaults from env to `deepseek-v4-flash` and honors `DEEPSEEK_MODEL` (R-073).
- Dump→report input shaping (R-040, R-041): generation request is built from the round's curated dump entries only; the response parses into ordered blocks.
- Tone request/parse (R-050, R-053): payload carries target block + report context; parsing enforces exactly 5 labeled samples.
- Critique request/parse (R-052, R-053): payload carries block + report context; the call path never mutates the block (R-052).
- Read-only invariant (R-011, R-012): drive a full reading → annotate → (mocked) generate → edit path at service level; assert the imported resource snapshot is byte-identical throughout and no code path writes resource content.
- Schema/CRUD round-trips: project, resources, rounds, dump entries, blocks; per-round stage transition `reading`→`editing`; after the shift, that round's round-bound operations (expert runs, dump curation) are rejected, while a new round in the same project starts in `reading` with them open again; annotation endpoints stay open — annotations are resource-scoped, not round-scoped (R-042 gate, DEC-006). Provider-column adoption (SD-20): a legacy project row created without `ai_provider` (pre-INT-007 shape) reads back as `deepseek` once the schema/column default is applied, and its in-app selector can still change it.

**Backend API tests** (TestClient, AI mocked) — §6 endpoint coverage per flow: tree reads (F1; import-upload coverage sits in its own paragraph below), annotations CRUD (F2), lens proposals + expert runs + merge-with-provenance (F3..F5), dump save/get (F6), generate-report returns blocks and flips the round's stage (F7/F8), block PUT persists manual edits (F9), tone-samples returns exactly 5 (F10), critique returns text without editing the block (F11), delete-report requires an explicit confirm payload (OQ-05). **Import-upload API tests (R-079..R-081)** — multipart POSTs through the TestClient `files=` API (gate-off default per SD-24): single-file upload → 201 `{"project_id", "imported_files": 1}` and the file snapshotted byte-for-byte (content round-trips through `GET /resources/{id}`), its node at the project root (`path == filename`, `parent_id` null); multi-file upload → 201 with the count and every file listed in `GET /projects/{id}/tree`; a `.markdown` file accepted; a batch containing a non-`.md`/`.markdown` part → 400 naming that file **and** nothing persisted (tree unchanged before/after); a batch whose parts all fail → 400; a request with no usable file part → 422/400 per R-080; duplicate file names in one request → 409 with nothing persisted; a second import on the same project → 409; unknown project → 404; invalid UTF-8 bytes → 400 naming the file; an empty (zero-byte) `.md` → 201 with empty content; an over-cap request → 413 (small cap injected at app creation per SD-29); gate-on instance: unauthenticated multipart upload → 401 `{"detail": "authentication required"}` — the gate covers multipart like every other `/api/v1` call (R-075; no CSRF bypass, SameSite=Lax, SD-27).

**Auth-gate API tests (R-075)** — two app-instance shapes: gate-off (plain `create_app()` — the default for the whole offline suite, unchanged pre-INT-006 behavior) and gate-on (`create_app(auth_key=...)`): `GET /login` → 200 HTML; `POST /login` with a wrong key → 401, no `Set-Cookie`, inline-error marker in the body; with the correct key → `Set-Cookie` (`wa_session`; HttpOnly, SameSite=Lax, Path=/; `Secure` only for https or `X-Forwarded-Proto: https` requests) + redirect to `/`; subsequent `/api/v1` calls through the TestClient cookie jar → 200, without a session → 401 `{"detail": "authentication required"}`; non-API paths without a session → 302 `/login`; `GET /login` with a valid session → 302 `/`; a tampered or expired cookie → 401; `POST /logout` → cookie cleared → the next API call is 401 again; a rotated key (different factory key) → the old cookie 401s. Gate-off instances expose none of it (`/login` → 404; every endpoint open).

**Static-serving tests (R-076)**: factory pointed at a fixture-built dist (tmp dir containing `index.html` + one hashed asset): `/` → `index.html`; `/assets/<hash>` → file bytes; a deep non-file path → `index.html` (SPA fallback); an unknown `/api/v1/*` path **with a valid session** → 404 unchanged (the fallback never swallows `/api`); a factory without a dist dir boots and serves the API only (no mount).
